# H6 capture contract 1.0.0

Separate strict format `resonance-h6-bundle`, protocol `offline-retro-h6-1.0.0-pilot`; [protocol](PROTOCOL.md). M0 v1.0.0 remains byte-for-byte frozen. The executable schema is schema.json; Python semantic validation additionally enforces scope, references, chronology, session completeness, question selection/version/cap, locks, preview and hashes. All native provider objects and response shapes are closed schemas. Unknown fields are rejected at the contract boundary; ingestion only collects its explicit scientific allowlist.

The age-encrypted container has exactly manifest.json, core/m0.zip, h6/evidence.json, export/preview.json, export/authorization.json and checksums.json. No extraction/network is used. Ciphertext/archive limit: 32 MiB; expanded outer limit: 48 MiB; component limit: 24 MiB. The inner core independently retains M0's unchanged archive/expansion/JSONL limits. H6 records are bounded to 60,000 and local participant import to 10,000 events. Unsafe paths, duplicates, symlinks, bad checksums, compressed expansion and malformed JSON are rejected.

Containing hash fields are excluded only from their own hash input. Each source record has exact record_hash; the envelope integrity_hash commits to exact logical content. Scientific content_hash uses a separate versioned domain, core scientific hash, ID-normalized H6 semantics and ordered membership/question arrays; volatile identities/generation clocks and the exact session-input hash are excluded (session event references/configuration and the core scientific hash commit to the scientific inputs) while meaningful consent/response clocks remain. canonical.mjs independently implements this projection over the frozen M0 RFC 8785 serializer; vectors/hashes.json contains cross-language bundle vectors.

RELEASE.json pins runtime/schema/question/consent/protocol/activation files. Synthetic fixtures/vectors are deliberately outside that runtime manifest to avoid a circular dependency on the release hash carried in fixture manifests. They are verified by the Python/JavaScript selftests and semantic validators. Both applications vendor the same release; do not independently edit specifications.

Existing generic immutable research capture tables store H6 records and their membership, plus the exact envelope. No event/answer/assignment rewrite or synthetic event migration is necessary. The protocol adapter extracts only the valid M0 core for existing materialization, then atomically stores the H6 source supplement. Local participant SQLite also uses its existing immutable record store; existing studies are not upgraded. New public study configs explicitly identify this release/protocol and require new consent.
